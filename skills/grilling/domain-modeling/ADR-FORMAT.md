# ADR 格式

ADR 存放在 `docs/adr/` 下，使用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

`docs/adr/` 目录按需懒创建——只在需要第一条 ADR 时才建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，为什么。}
```

就这些。一条 ADR 可以只有一段话。价值在于记录*做过*这个决策以及*为什么*——而不是填满各个小节。

## 可选小节

只在真正增加价值时才包含以下内容。大多数 ADR 用不到它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——决策可能被重审时有用
- **Considered Options**——只当被否决的备选方案值得记住时
- **Consequences**——只当有不直观的下游影响需要点明时

## 编号

扫描 `docs/adr/` 找到当前最大编号，加一。

## 何时提议 ADR

以下三条必须同时成立：

1. **难以逆转**——日后改主意的代价是实打实的
2. **没有上下文会显得反常**——未来的读者看到代码会纳闷"当初到底为什么这么做？"
3. **源自真实的取舍**——确实存在过备选方案，你基于具体理由选了其一

如果决策容易逆转，跳过——反正你会直接改回来。如果并不反常，没人会好奇为什么。如果没有过真正的备选，那除了"我们做了显而易见的选择"之外也没什么可记的。

### 什么够格

- **架构形态。** "我们用 monorepo。""写模型是 event-sourced，读模型投影到 Postgres。"
- **context 之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，不走同步 HTTP。"
- **带来锁定的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库都算——只算那些要花一整个季度才能换掉的。
- **边界与范围决策。** "Customer 数据归 Customer context 所有；其他 context 只按 ID 引用。"明确的"不做什么"和"做什么"同样有价值。
- **有意偏离常规路径。** "我们用手写 SQL 而不用 ORM，因为 X。"任何让合理读者会默认相反的决策。这能阻止下一个工程师去"修复"一个有意为之的东西。
- **代码里看不见的约束。** "因为合规要求不能用 AWS。""响应时间必须在 200ms 以内，因为合作方 API 合同这么定的。"
- **被否决的备选方案（当否决理由不直观时）。** 如果你评估过 GraphQL 却因微妙的理由选了 REST，记下来——否则六个月后还会有人再提 GraphQL。
