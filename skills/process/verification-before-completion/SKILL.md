# 完成前验证

完成声明必须建立在当前代码状态的证据上。验证的目的不是重复整个开发流程，而是确认最终结果是否足以交付。

> 【老王注】一句话：先确定要证明什么，再运行对应检查，最后只说证据支持的话。

## 验证门禁

在作出完成、修复成功或检查通过的结论前：

1. **明确结论：**列出准备声称的结果和本次任务的验收条件。
2. **选择证据：**为每项结论选择最小但充分的检查，例如测试、类型检查、lint、构建、复现步骤或需求清单。
3. **运行检查：**在最后一次相关改动之后执行检查，阅读完整输出并确认退出码和失败项。
4. **对照结果：**确认每项结论都有证据支持；不要用一种检查代替另一种检查。
5. **报告状态：**先给出验证证据，再给出结论；同时列出无法验证的部分、原因和剩余风险。

## 证据范围

| 准备声明 | 至少需要 |
|----------|----------|
| 测试通过 | 对应测试命令成功，且没有失败项 |
| 构建或类型正确 | 对应构建或类型检查命令成功 |
| 缺陷已修复 | 原始复现路径或回归测试通过 |
| 需求已满足 | 对照验收条件逐项确认 |
| Agent 任务已完成 | 检查实际 diff，并独立运行相关验证 |

只运行与改动无关的检查、引用修改前的结果，或说“应该没问题”，都不足以支持完成声明。

## 无法完整验证时

不要为了得到绿色结果而扩大修改范围或隐藏失败。若环境、权限、依赖或时间限制导致检查无法运行：

- 说明已经验证的内容及结果；
- 说明未验证的内容及原因；
- 不把部分验证表述为全部完成；
- 给出最直接的后续验证命令或步骤。

## 汇报格式

```text
验证：<命令或检查> -> <关键结果>
未验证：<项目与原因；没有则省略>
结论：<仅包含证据能够支持的状态>
```

验证不替代代码审查，也不要求重做 TDD；它只负责在交付结论前建立可信证据。
