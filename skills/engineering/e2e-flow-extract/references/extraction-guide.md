# 从源码抽离 E2E 流程的方法

本指南帮助识别可验证的用户旅程，并区分首次抽离、新增流程和已有流程的变化。目标是得到可复核的业务契约，而不是自动猜测测试脚本。

## 从入口开始

优先寻找以下证据，再沿依赖关系向下阅读：

| 证据 | 常见位置 | 可回答的问题 |
|---|---|---|
| 路由与导航 | router、pages、menu、导航组件 | 用户从哪里进入？哪些角色可见？ |
| 页面/视图 | 页面组件、模板、服务端渲染视图 | 用户做什么？界面上会看到什么？ |
| 状态与权限 | middleware、guards、policy、store | 谁能执行？认证或数据前置是什么？ |
| 控制器与领域服务 | controllers、handlers、services | 业务动作导致的状态变化是什么？ |
| 已有测试 | e2e、integration、unit | 已验证什么？有哪些可靠 locator 或测试数据来源？ |
| 文档 | README、产品说明、接口契约 | 术语和高层目标是什么？ |

不要把接口或数据库模型本身当成流程。它们只用于确认页面行为背后的业务结果。

## 候选流程筛选

用下面的句式写出候选，再决定是否建模：

> `<persona>` 从 `<entry>` 开始，完成 `<goal>`，并能观察到 `<expected result>`。

保留满足以下条件的候选：

1. 有明确的用户角色和可感知目标。
2. 有可从源码验证的入口和成功信号。
3. 对用户价值、风险或回归成本有意义。
4. 能在合理的 E2E 边界内完成，而不是跨多个独立产品或人工审批链路。

不单独建模：纯 API 调用、只有内部定时任务、无用户可观察结果的技术迁移、同一目标的微小 UI 操作，或缺少证据的推测。

## 三种维护场景

### 首次抽离

从目录、路由和导航建立覆盖图。按 persona 聚合目标，选择少量高价值流程作为基线。首次抽离不等于“列完所有功能”：要在报告中同时写已覆盖区域和未覆盖区域。

如果登录后的区域无法用本地环境或源码确认，不要编造账号或数据。登记需要的环境变量名，并把环境缺口写入存疑项。

### 旧项目新增流程

先读取现有流程，尤其比较 `persona + goal + entry`。出现新页面并不必然是新流程：

- 新页面只是旧目标中的下一步：更新原流程，或仅更新其溯源。
- 同一角色获得了新的独立目标：创建新流程。
- 新角色沿不同权限完成同一目标，且成功条件不同：通常创建新流程。
- 新 API 仅替代内部实现：不创建流程。

若用户提供分支、提交范围或 PR，使用它缩小阅读范围；若未提供，明确报告“当前代码分析，未验证历史变更”。

### 原流程有改动

先以 YAML 作为待验证假设，而非真相。逐项核对 `persona`、`goal`、`entry`、关键 `steps`、`expected/signal`、`sources` 和 `paths`。

| 发现 | 分类 | 处理 |
|---|---|---|
| 管理员现在必须审批后用户才能提交 | 业务语义变化 | 更新同一流程，重置为 `draft`、`enabled: false`。 |
| 登录后的首页从 `/home` 改为 `/dashboard`，且旧入口失效或用户实际入口改变 | 业务语义变化 | 更新 entry/signal，重置为 `draft`、`enabled: false`。 |
| `/home` 仍重定向到同一工作台，只是规范 URL 改为 `/dashboard` | 纯实现变化 | 保留生命周期；按需要更新 sources/paths，并移交③复核测试。 |
| 表单组件重写，但目标、入口和成功结果不变 | 纯实现变化 | 保留生命周期；更新溯源，移交③复核测试。 |
| 文案从“保存”改为“提交”，无法判断结果是否变化 | 不确定 | 不改流程，报告需要的产品确认。 |

如果一个流程被拆成多个独立目标或多个目标被合并，先列出 proposed mapping，例如 `old-checkout → checkout-payment + checkout-confirmation`，请求确认后再创建或退休流程。不要静默删除旧 YAML。

## 信号与选择器线索

`signal` 只是给③的断言方向。优先从源码记录这些可复核线索：

1. 稳定路由或页面标题。
2. 可访问角色和名称（button、heading、dialog 等）。
3. label 与表单字段关联。
4. 约定的 `data-testid` / `data-test` 属性。
5. 稳定、面向用户的文本。

不要以样式类、DOM 层级或位置序号作为流程信号。找不到可靠信号时，照实记录“需③在实现时复核”，而非伪造 locator。

## 报告前的复核问题

- 每条流程是否刚好表达一个角色和一个目标？
- 新增项是否真的不是现有流程的一部分？
- 修改项是否真的改变了用户看到的业务契约？
- 每个入口、信号和来源文件是否有证据？
- 人工模式下的新流程和业务语义更新是否均为 `draft`、`enabled: false`？显式 `source-validated` 模式中，只有证据齐全、无存疑且完整校验通过的条目可为 `ready`，但仍须 `enabled: false`。
- 是否报告了未覆盖的区域、环境限制和不确定问题？
