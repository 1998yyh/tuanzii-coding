# 测试驱动开发（TDD）

TDD 是 red → green 循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好测试、测试写在哪里、有哪些反模式、循环的规则。每一节在每个循环周期都适用——在循环之前和之中查阅，而不是之后。

探索代码库时，阅读 `CONTEXT.md`（如果存在），让测试名和接口词汇与项目的领域语言保持一致，并遵守你即将改动区域的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是验证实现细节。实现可以完全重写，测试不应随之改变。好测试读起来像规格说明——"user can checkout with valid cart"直接告诉你系统具备什么能力——并且因为不关心内部结构而能在重构后存活。

示例见 [tests.md](tests.md)，mocking 准则见 [mocking.md](mocking.md)。

## Seam——测试写在哪里

**Seam** 是你在其上测试的公开边界：在这个接口上观察行为，而不必伸手进入内部。测试只存在于 seam 上，绝不针对内部实现。

**只在事先约定的 seam 上测试。** 写任何测试之前，先写下要测的 seam 并与用户确认。未经确认的 seam 上不写测试。你不可能测试一切——事先约定 seam，是让测试投入落在关键路径和复杂逻辑上、而不是每个边角案例上的方法。

问："公开接口是什么？我们应该在哪些 seam 上测试？"

当接口本身的形状存疑时——模块该多深、seam 该放在哪、接口该暴露什么——使用 `tuanzii:codebase-design` skill 的词汇。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同来源，是一份供查阅的参考，不是一个要走完的流程。

## 反模式

- **耦合实现** —— mock 内部协作者、测试私有方法、或通过旁路验证（查数据库而不是走接口）。识别信号：重构后行为没变，测试却挂了。
- **同义反复（tautological）** —— 断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、手工以同样方式推导的 snapshot、常量断言等于自身），因此它在构造上必然通过，永远不可能与代码产生分歧。期望值必须来自独立的真相来源——一个已知正确的字面量、一个手工演算过的例子、规格文档。
- **水平切片** —— 先写完所有测试，再写所有实现。批量测试验证的是_想象中的_行为：你测的是事物的_形状_而不是面向用户的行为，测试对真实变化失去敏感性，并且在理解实现之前就把测试结构定死了。改用**垂直切片**——一个测试 → 一个实现 → 重复，每个测试都是一颗** tracer bullet**，根据上一个循环学到的东西做出响应。

## 循环的规则

- **先 red 后 green。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，不要添加投机性的功能。
- **一次一个切片。** 每个循环周期：一个 seam、一个测试、一个最小实现。
- **重构不属于循环。** 它属于评审阶段（见 `tuanzii:code-review` skill），不属于 red → green 实现循环。
