# Wizard

**Wizard** 是一个 bash 脚本，一步步引导人类走完一套手工流程 —— 手工做很繁琐、每次重新向 AI 解释也很繁琐的那种。它打开每个 URL、精确说明要点哪里、复制什么，捕获各个值、写到它们该在的地方（`.env`、GitHub secrets），在每个阶段确认，并显示还剩几个阶段。它可能配置第三方服务、执行一次性迁移，或把项目从一种状态迁移到另一种状态。

愉悦的交互体验已经由 [template.sh](template.sh) 解决了 —— 逐阶段进度、确认门、跨平台打开 URL（含 WSL）、隐藏式 secret 输入、幂等的 `.env` upsert、`gh secret` / `gh variable` 写入，以及结尾总结。**你的工作只是界定流程并编写各个阶段。** `STAGES` 标记以上的库代码在每个 wizard 中都完全相同；这种一致性正是意义所在 —— 绝不手工改动它。

Wizard 默认是一次性的 —— 为一次运行而建，存到 scratch 或 `scripts/` 路径，活干完就删。只有当用户想要一个应该留在仓库里的可复用配置路径时才提交它。

## 流程

### 1. 界定流程

理出人类必须执行的每个手工步骤，以及沿途要捕获的每个值。先读仓库 —— 不要空问：

- 对配置类任务：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是 wizard 必须产出的一个值）。
- 对迁移或切换类任务：当前状态、目标状态，以及两者之间不可逆的操作。

然后向用户展示按序排列的阶段清单和每个阶段产出的值，并确认 —— 他们可能会增、删或重排。

**完成标准：** 每个阶段都按序命名，且对每个要捕获的值你都知道：(a) 人类从哪里拿到它，(b) 它写到哪里（`.env`、GitHub secret、两者，或都不写 —— 有些阶段是纯操作），(c) 它是 secret（隐藏输入）还是公开的。

### 2. 绘制每个阶段的路径

为每个阶段写出人类要走的精确路径：打开哪个 URL、在那里做什么、值显示在哪里、填入哪个变量 —— 例如 "Dashboard → Developers → API keys → Reveal test key → copy"。凡是你不确切知道当前 UI 或确切命令的地方，明说并问用户或查文档 —— 绝不编造可能不存在的步骤。

**完成标准：** 每个阶段都能落到陌生人也能照着走的具体指引。

### 3. 编写 wizard

把 `template.sh` 复制到目标路径。用每步一个 `stage` 替换示例阶段，按依赖顺序排列。使用库提供的辅助函数 —— `stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm` —— 并把 `TOTAL_STAGES` 设为你写的阶段数。

守住模板设定的标准：先打开 URL 再要它的值；任何 secret 都用 `ask_secret`；每个要持久化的值都 `write_env`；只有 CI 真正需要的值才 `set_secret`；任何不可逆操作之前都 `confirm`。每个 `stage` 会清屏，只显示当前步骤 —— 让一个阶段只聚焦一件事，人类需要的信息才不会被滚走。不要动标记线以上的库代码。

### 4. 验证并交付

- `bash -n <script>`；有 `shellcheck` 就跑一下。
- `chmod +x <script>`。
- 不要自己端到端运行它 —— 它会打开浏览器并阻塞等待人类输入。改为静态走查：第 1 步里的每个值都被捕获并落到了第 1 步所说的位置，每个 `set_secret` 的名字都与 CI 中的 `secrets.*` 引用精确一致。
- 告诉用户怎么运行它。如果它是可复用的配置路径，提交它并在 README 里链接，让下一个人直接跑脚本，而不是再去问 AI。
