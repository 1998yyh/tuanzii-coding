# Design It Twice（设计两遍）

当用户想为一个选定的深化候选探索备选接口时，使用这个并行 subagent 模式。基于 "Design It Twice"（Ousterhout）—— 你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 的词汇 —— **module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 框定问题空间

派 subagent 之前，先为选定的候选写一份面向用户的问题空间说明：

- 任何新接口都必须满足的约束
- 它会依赖什么、这些依赖属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意代码草图，让约束落到实处 —— 不是提案，只是把约束具象化

把这份说明给用户看，然后立即进入第 2 步。subagent 并行工作期间，用户边读边想。

### 2. 派 subagent

并行派出 3 个以上 subagent。每个都必须为深化后的模块产出一个**截然不同的**接口。

给每个 subagent 一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、seam 后面藏着什么）。简报与第 1 步面向用户的问题空间说明相互独立。给每个 agent 一个不同的设计约束：

- Agent 1："最小化接口 —— 目标最多 1–3 个入口点。最大化每个入口点的 leverage。"
- Agent 2："最大化灵活性 —— 支持多种用例和扩展。"
- Agent 3："为最常见的调用方优化 —— 让默认场景用起来毫不费力。"
- Agent 4（如适用）："围绕 ports & adapters 设计，处理跨 seam 依赖。"

简报里同时包含 [SKILL.md](SKILL.md) 的词汇和 CONTEXT.md 的词汇，让每个 subagent 的命名都与架构语言和项目领域语言保持一致。

每个 subagent 输出：

1. 接口（类型、方法、参数 —— 外加不变量、顺序、错误模式）
2. 展示调用方如何使用它的用例
3. 实现把什么藏在 seam 后面
4. 依赖策略与 adapter（见 [DEEPENING.md](DEEPENING.md)）
5. 取舍 —— 哪里 leverage 高，哪里单薄

### 3. 展示与对比

逐个展示设计，让用户能消化每一个，然后用散文对比。按**深度**（接口处的 leverage）、**局部性**（变更集中在哪里）和 **seam 位置**三个维度对照。

对比之后给出你自己的推荐：你认为哪个设计最强、为什么。如果不同设计的元素能很好地组合，提出一个混合方案。要有主见 —— 用户要的是一个明确的判断，不是一份菜单。
