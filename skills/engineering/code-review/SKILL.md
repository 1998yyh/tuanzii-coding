对 `HEAD` 与用户提供的固定点之间的 diff 做双轴评审：

- **Standards** —— 代码是否符合本仓库成文的编码规范？
- **Spec** —— 代码是否忠实实现了原始 issue / spec？

两条轴以**并行 subagent** 方式运行，互不污染上下文，然后由本 skill 汇总两者的发现。

issue tracker 应该已经提供给你了 —— 如果 `docs/agents/issue-tracker.md` 缺失，先运行 tuanzii:setup-matt-pocock-skills。

## 流程

### 1. 钉住固定点

用户说的那个就是固定点 —— commit SHA、分支名、tag、`main`、`HEAD~5` 等等。没指定就问。

diff 命令只确定一次：`git diff <fixed-point>...HEAD`（三点语法，即对照 merge-base 比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

继续之前，先确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏引用或空 diff 应该在这里就失败 —— 而不是失败在两个并行 subagent 内部。

### 2. 找到 spec 来源

按以下顺序寻找原始 spec：

1. commit 消息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）—— 按 `docs/agents/issue-tracker.md` 里的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或特性匹配的 spec 文件。
4. 都没找到就问用户 spec 在哪。如果用户说没有，**Spec** subagent 跳过并在报告里注明"无 spec 可用"。

### 3. 找到规范来源

仓库里任何记录"代码该怎么写"的文档，比如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

在仓库成文规范之上，Standards 轴永远带着下面的**坏味道基线（smell baseline）** —— 一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也适用。它受两条规则约束：

- **仓库优先。** 成文的仓库规范永远胜出；凡仓库明确认可、而基线会标记的写法，压制该坏味道。
- **永远是判断题。** 每个坏味道都是带标签的启发式（"疑似 Feature Envy"），绝不是硬性违规 —— 并且和这里的任何规范一样，工具已经强制检查的东西一律跳过。

每个坏味道按*是什么* → *怎么修*来读；对着 diff 匹配：

- **Mysterious Name（神秘命名）** —— 函数、变量或类型的名字看不出它做什么、装什么。→ 重命名；如果想不出诚实的名字，说明设计本身就是浑的。
- **Duplicated Code（重复代码）** —— 同样的逻辑形状出现在改动的多个 hunk 或文件里。→ 抽出共享形状，两处都调用它。
- **Feature Envy（依恋情结）** —— 一个方法伸手摸别的对象的数据多过用自己的。→ 把方法搬到它羡慕的数据上。
- **Data Clumps（数据泥团）** —— 同样的几个字段或参数总是结伴出现（一个想出生的类型）。→ 打包成一个类型，传这个类型。
- **Primitive Obsession（基本类型偏执）** —— 用基本类型或字符串顶包一个值得拥有自己类型的领域概念。→ 给这个概念一个小类型。
- **Repeated Switches（重复的 switch）** —— 针对同一类型、同样的 `switch`/`if` 级联在改动里反复出现。→ 换成多态，或两处共享的一张映射表。
- **Shotgun Surgery（霰弹式修改）** —— 一个逻辑变更迫使 diff 里许多文件被零散地改。→ 把一起变的东西收进同一个模块。
- **Divergent Change（发散式变化）** —— 一个文件或模块因为多个不相干的原因被改。→ 拆到每个模块只为一个原因而变。
- **Speculative Generality（夸夸其谈的通用性）** —— 为 spec 里不存在的需要而加的抽象、参数或钩子。→ 删掉；内联回去，直到真实需要出现。
- **Message Chains（消息链）** —— 调用方不该依赖的长 `a.b().c().d()` 导航。→ 把这条路径藏在第一个对象的一个方法后面。
- **Middle Man（中间人）** —— 一个基本只负责转发的类或函数。→ 砍掉它，直接调真正的目标。
- **Refused Bequest（拒绝的遗赠）** —— 子类或实现者忽略或覆盖掉继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行派出两个 subagent

**Standards subagent 的 prompt** —— 包含：

- 完整的 diff 命令和 commit 列表。
- 第 3 步找到的规范来源文件列表，**外加第 3 步的坏味道基线全文粘贴** —— subagent 没有其他途径拿到它。
- 简报："报告 —— 按文件/hunk（相关处）列出 —— (a) diff 违反成文规范的每一处：引用规范（文件 + 具体规则）；(b) 你发现的任何基线坏味道：命名它并引用对应 hunk。区分硬性违规与判断题 —— 违反成文规范可以是硬性违规，但基线坏味道永远是判断题，且成文的仓库规范覆盖基线。工具已强制的检查一律跳过。400 词以内。"

**Spec subagent 的 prompt** —— 包含：

- diff 命令和 commit 列表。
- spec 的路径或取回的内容。
- 简报："报告：(a) spec 要求了但缺失或只做了一半的需求；(b) diff 里没人要求的行为（scope creep）；(c) 看似已实现、但实现看起来不对的需求。每条发现引用对应的 spec 原文行。400 词以内。"

如果 spec 缺失，跳过 Spec subagent 并在最终报告里注明。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 标题下呈现，原文照录或轻微清理。**不要**合并或重新排序发现 —— 两条轴是刻意分开的（见「为什么两条轴」）。

最后用一行总结收尾：每条轴的发现总数，以及*每条轴内部*最严重的问题（如果有）。不要跨轴选一个总冠军 —— 分轴存在的目的正是防止这种重新排序。

## 为什么两条轴

一个改动可能过一轴、挂一轴：

- 代码符合每一条规范、但实现错了东西 → **Standards 过，Spec 挂。**
- 代码精确实现了 issue 的要求、但破坏了项目惯例 → **Spec 过，Standards 挂。**

分开汇报可以防止一条轴掩盖另一条。
