# Diagnosing Bugs

一套针对疑难 bug 的纪律。只有明确有理由时才允许跳过阶段。

探索代码库时，读 `CONTEXT.md`（如果存在）来建立相关模块的清晰心智模型，并查看你触及区域的 ADR。

## 脱敏

本 skill 会让你展示命令、输出和抓取的产物。**先把每个 secret 脱敏** —— 原位写上 `<REDACTED>`。反馈回路要对着环境变量构建，让凭据留在环境里，而不是出现在你展示的内容里。抓取的产物带有 auth header：只引用承载信号的那几行。

如果脱敏后的输出不足以诊断 bug，明说，然后问用户。

## 阶段 1 —— 构建反馈回路

**这就是本 skill 的本体。** 其余一切都是机械动作。如果你有一个针对这个 bug 的**紧凑**通过/失败信号 —— 一个会因*这个* bug 变红的信号 —— 你就一定能找到原因；二分、假设检验、插桩全都只是消耗它。如果你没有，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要激进。要有创造力。拒绝放弃。**

### 构建方法 —— 大致按此顺序尝试

1. **失败测试**，打在能触达 bug 的任何 seam 上 —— 单元、集成、e2e。
2. **Curl / HTTP 脚本**，对着跑起来的 dev server。
3. **CLI 调用**，喂 fixture 输入，把 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，断言 DOM/console/网络。
5. **重放抓取的 trace。** 把真实的网络请求 / payload / 事件日志存到磁盘；隔离地重放穿过那段代码路径。
6. **一次性 harness。** 拉起系统的最小子集（一个服务、mock 掉依赖），用一次函数调用触发 bug 代码路径。
7. **Property / fuzz 循环。** 如果 bug 是"有时输出不对"，跑 1000 个随机输入找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化"在状态 X 启动、检查、重复"，好让你能 `git bisect run` 它。
9. **差分循环。** 同一输入分别跑旧版本和新版本（或两套配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人工点击，用 `scripts/hitl-loop.template.sh` 驱动*那个人*，让循环仍然是结构化的。抓到的输出回喂给你。

构建正确的反馈回路，bug 就修好了 90%。

### 收紧回路

把回路当产品打磨。有了*一个*回路之后，**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是"没崩溃"。）
- 能更确定吗？（钉住时间、seed RNG、隔离文件系统、冻结网络。）

30 秒且 flaky 的回路比没有回路强不了多少；2 秒且确定的回路才叫紧凑 —— 是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发循环 100 遍、并行化、加压力、收窄时序窗口、注入 sleep。50% 复现率的 flaky bug 是可调试的；1% 不是 —— 持续提升复现率，直到它可调试。

### 当你真的建不出回路

停下来，明说。列出你试过的方法。向用户要：(a) 能复现问题的环境的访问权，(b) 脱敏后的抓取产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。没有回路就**不要**进入假设阶段。

### 完成标准 —— 一个会变红的紧凑回路

当回路**紧凑**且**可变红（red-capable）**时，阶段 1 完成：你能说出**一条命令** —— 脚本路径、测试调用、curl —— 你**已经至少跑过一次**（展示调用及其脱敏后的输出），并且它满足：

- [ ] **可变红** —— 它驱动真实的 bug 代码路径，断言**用户描述的精确症状**，因此它能因这个 bug 变红、修复后变绿。不是"跑起来不报错" —— 它必须能*抓住这个特定的 bug*。
- [ ] **确定** —— 每次运行结论一致（flaky bug：按上文钉住的高复现率）。
- [ ] **快** —— 秒级，不是分钟级。
- [ ] **agent 可运行** —— 你可以无人值守地跑它；只有经由 `scripts/hitl-loop.template.sh` 才允许人在环。

如果你发现自己在写出这条命令之前就在读代码构建理论，**停下 —— 直接跳到假设正是本 skill 要防的那个失败。** 没有可变红的命令，就没有阶段 2。

## 阶段 2 —— 复现 + 最小化

跑回路。看着它变红 —— bug 出现了。

确认：

- [ ] 回路产生的失败模式就是**用户**描述的那个 —— 不是恰好躺在旁边的另一个失败。bug 错了 = 修复也错。
- [ ] 失败在多次运行中可复现（或者，对非确定性 bug，复现率高到足以对着它调试）。
- [ ] 你已捕获精确症状（错误消息、错误输出、缓慢的耗时），后续阶段可以据此验证修复确实对症。

### 最小化

变红之后，把复现缩到**仍然会变红的最小场景**。输入、调用方、配置、数据、步骤，**一次只砍一个**，每砍一刀重跑一遍回路 —— 只保留对失败起承重作用的部分。

为什么要费这事：最小复现能压缩阶段 3 的假设空间（剩下的可疑活动部件更少），并在阶段 5 变成干净的回归测试。

完成标准：**剩下的每个元素都是承重的** —— 去掉任何一个，回路就变绿。

复现**且**最小化之前，不要继续。

## 阶段 3 —— 假设

先产出 **3–5 个排好序的假设**，再测试其中任何一个。只产出一个假设会让你锚死在第一个看似合理的想法上。

每个假设必须**可证伪**：说出它的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更严重。"

说不出预测的假设是一种 vibe —— 丢弃或打磨它。

**测试之前把排好序的清单给用户看。** 他们常常握有能立刻改变排序的领域知识（"我们刚部署了对 #3 的改动"），或者知道某些假设已被排除。低成本的检查点，省大时间。不要阻塞在这上面 —— 用户不在就按你的排序继续。

## 阶段 4 —— 插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持就用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界处打**定向日志**。
3. 永远不要"全都记下来再 grep"。

**给每条调试日志打唯一前缀**，如 `[DEBUG-a4f2]`。收尾清理就是一次 grep。没标签的日志会活下来；有标签的必须死。

**性能分支。** 对性能回归，日志通常是错的工具。改为：先建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），再二分。先测量，后修复。

## 阶段 5 —— 修复 + 回归测试

回归测试写在修复**之前** —— 但前提是存在一个**正确的 seam**。

正确的 seam 是指测试能按调用现场的真实样子触发**真实的 bug 模式**。如果唯一可用的 seam 太浅（bug 需要多个调用方而测试只有一个、单元测试复制不出触发 bug 的调用链），在那里写回归测试只会带来虚假的信心。

**如果不存在正确的 seam，这本身就是发现。** 记下来。是代码库架构在阻止这个 bug 被锁死。为下一阶段标记它。

如果存在正确的 seam：

1. 把最小化复现变成该 seam 上的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 用原始（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6 —— 清理 + 事后复盘

宣布完成之前必须：

- [ ] 原始复现不再复现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或已记录不存在 seam）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 那个前缀）
- [ ] 一次性 prototype 已删除（或移到明确标记的调试位置）
- [ ] 最终被证实的假设写进了 commit / PR 消息 —— 让下一个调试者学到东西

**然后问：什么能从一开始就防住这个 bug？** 如果答案涉及架构变更（没有好的测试 seam、调用方纠缠、隐藏耦合），带着具体细节交接给 tuanzii:improve-codebase-architecture。这个建议要**在修复落地之后**提，而不是之前 —— 此刻你掌握的信息比开始时多。
