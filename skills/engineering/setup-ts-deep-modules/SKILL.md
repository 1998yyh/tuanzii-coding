# 配置 TypeScript 深模块（实验版）

本技能迁自上游 `in-progress/`，属于实验版，仅在用户显式调用时执行。

让仓库中的每个包成为**深模块**：用小接口承载丰富行为。包的公共接口是**入口文件**（包根目录下的文件），子目录中的内容则保持私有。本技能安装 [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)，配置只能通过入口访问包的规则，再验证违规确实会被拦截。

通过宿主的技能加载机制调用 `tuanzii:codebase-design` 技能，了解深模块、接口、接缝、深度等术语，并在后续使用同一套语言。

## 要落实的目录结构

```text
src/packages/
  <name>/
    index.ts        ← 公共入口，包外代码从这里导入。
    client.ts       ← 另一个入口；一个包可以提供多个入口。
    lib/            ← 实现：对包外隐藏，内部实现文件可以互相导入。
    tests/          ← 共置的测试和夹具；位于子目录，因此是私有内容。
```

公共接口是包的**所有根目录文件**，并非某个指定的 `index.ts`。约定把实现放在 `lib/`，测试放在 `tests/`，让各包都有相同的双目录结构。不过，边界规则适用于**任意子目录中的任意内容**，新增私有目录无需扩展配置。

模板实际包含五条 `forbidden` 规则，级别均为 `error`：

1. **应用入口边界**（`entrypoint-boundary-from-app`）：包目录之外的应用或根目录代码，只能导入包的根目录入口文件，不能导入子目录内容。
2. **跨包入口边界**（`entrypoint-boundary-across-packages`）：包内非测试代码只能通过其他包的根目录入口访问它们；访问本包实现不受这条规则限制。
3. **测试通过入口访问**（`tests-through-entrypoints`）：`<pkg>/tests/` 中的文件可以导入任意包的入口和本包 `tests/` 中的夹具，但不能导入任何包的其他内部子目录，包括本包的实现。允许跨包集成测试。
4. **测试目录私有**（`tests-folder-is-private`）：非测试代码不能导入任何包的 `tests/` 内容，包括本包的测试夹具；结合上一条，测试也不能访问其他包的夹具。
5. **禁止循环依赖**（`no-circular`）：检查范围内不允许出现依赖环。

包内实现文件可以互相导入；这项自由仍受测试目录私有和禁止循环依赖两条规则约束。

**入口应当小而明确。** 一个包可以提供多个小入口（`index.ts`、`client.ts`、`server.ts`），无需把所有内容汇入巨大的 `index.ts`。不鼓励通过 barrel 文件重导出整个子树；保持入口精简，把实现隐藏在子目录中。

分层规则决定哪些包可以依赖哪些包，是另一项职责。模板仅留下被注释的示例，由目标仓库按需补充。

## 步骤

### 1. 识别环境

- **包管理器**：优先遵循仓库已有的 `packageManager` 声明和工作流；否则按锁文件识别：`pnpm-lock.yaml` → pnpm，`yarn.lock` → yarn，`bun.lock` 或 `bun.lockb` → bun，其他情况使用 npm。多个锁文件冲突时核对 CI 和仓库说明。后续安装、脚本和命令均使用同一包管理器。
- **包目录**：先检查已有约定；没有约定时，有 `src/` 则采用 `src/packages`，否则采用 `packages`。沿用明显存在的包目录；只有无法确定时才向用户澄清。
- **扫描入口**：识别实际应用源码目录和包目录，例如 `src`、`app`、`apps`、`packages`。检查必须同时覆盖包外调用方和包，才能发现应用深导入。记录应传给 `depcruise` 的实际目录，不能仅扫描包目录。
- **已有配置**：检查 `.dependency-cruiser.*` 及现有脚本指定的配置文件。保留已有配置，将五条规则和必要选项合并进去，并向用户说明新增内容。
- **已有示例**：检查 `<packages-root>/example/`；保留已有内容，避免覆盖。若无法复用，选择一个未占用的示例包名，后续步骤使用该名字。

**完成标准：** 包管理器、包目录、全部扫描入口、已有配置与示例状态均已确认。

### 2. 安装 dependency-cruiser

使用已识别的包管理器，将与目标仓库 Node 和 TypeScript 版本兼容的 `dependency-cruiser` 安装为开发依赖。核对已安装工具的版本要求与解析器状态；缺少兼容解析器时，选择兼容的工具版本或受支持的适配方式，不擅自升级或降级项目 TypeScript。

**完成标准：** `devDependencies` 中存在兼容的 `dependency-cruiser`，或已明确说明未解决的兼容性阻塞；后者不能继续宣称边界检查已配置成功。

### 3. 写入配置

没有已有配置时，将 [`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs) 复制到仓库根目录，命名为 `.dependency-cruiser.cjs`。已有配置时按步骤 1 合并，保留原有规则和选项。将 `PACKAGES_ROOT` 设为步骤 1 确认的包目录。规则按路径深度判断边界，与文件扩展名无关，无需为每个包或内部目录分别添加规则。

**完成标准：** 生效配置中的 `PACKAGES_ROOT` 正确，五条 `forbidden` 规则均已配置，原有配置内容得以保留。

### 4. 接入检查命令

- 添加或合并 `lint:boundaries` 脚本，显式使用步骤 3 的配置和步骤 1 确认的全部扫描入口。例如应用与包均在 `src/` 下时使用 `depcruise --config .dependency-cruiser.cjs src`；应用在 `app/`、包在 `packages/` 时使用 `depcruise --config .dependency-cruiser.cjs app packages`。目录与配置名必须根据目标仓库调整。
- 将脚本接入仓库已有的综合检查命令，即包含类型检查的 `check`、`ci` 或 `validate` 等命令。保持目标仓库的 `tsconfig` 不变，也不添加路径别名。
- 没有综合检查命令时，只添加 `lint:boundaries`，告知用户如何将它接入 CI。

**完成标准：** `lint:boundaries` 覆盖实际应用目录和包目录，并已接入现有综合检查命令；若不存在综合命令，则已提供独立脚本和 CI 接入说明。

### 5. 创建示例包

在 `<packages-root>/example/` 创建可复制的起步模板；已有内容按步骤 1 保留或换用未占用的包名：

- `index.ts` 是入口，导出一个委托内部文件完成行为的函数，让包展示出深模块结构。
- `lib/impl.ts` 是位于**子目录**中的实现，由 `index.ts` 导入，包外代码无法直接访问。
- `tests/example.test.ts` 通过 `../index` 导入公共函数并断言其行为；测试框架导入遵循仓库现有约定。

告诉用户，这个起步模板可以复制或删除。将文件留在工作区供检查；只有用户明确要求提交时才执行 `git commit`，并遵循目标仓库的提交规范。

**完成标准：** 示例包存在，通过根目录入口暴露行为，`impl` 隐藏在子目录中，原有示例内容得以保留。

### 6. 证明规则有效

这是整个技能的完成标准：配置必须能让实际违规检查失败。

1. 运行 `lint:boundaries`。干净示例必须**通过**。再用相同配置和入口输出 JSON（`--output-type json`），核对 `summary.environment` 中 TypeScript 解析器与扩展名可用、`modules` 包含示例的 `.ts` 文件及实际应用入口、依赖边确实存在。只返回退出码 0 或扫描模块数为 0，都不能作为通过证据。若仓库已有边界违规，先报告并在已授权范围内处理；尚未通过时不能声称完成。
2. 暂时在 `tests/example.test.ts` 中添加对 `../lib/impl` 的深导入，并实际使用导入的符号，避免未使用导入被分析器忽略。再次运行，必须**失败**并报告 `tests-through-entrypoints`。
3. 撤销自己刚添加的违规代码，再次运行，必须**通过**。任何中途失败也要清理自己添加的临时违规，保留用户原有改动。

同时核验应用边界覆盖：在实际被扫描的应用目录中暂时添加并使用对示例包 `lib/impl` 的深导入，确认检查以 `entrypoint-boundary-from-app` 失败，撤销后再确认通过。这样才能证明检查入口没有漏掉包外调用方。

**完成标准：** 亲眼观察到通过 → 违规失败 → 恢复通过，测试深导入和应用深导入均触发对应规则。如果违规没有失败，先修正配置或扫描入口，再重新验证。

### 7. 记录约定

在**包目录中**编写 `<packages-root>/README.md`，与它约束的包放在一起；已有 README 时合并相关说明。内容包括实际目录布局（根目录放入口，`lib/` 放实现，`tests/` 放测试）、“只能通过包的根目录入口文件导入”，以及如何运行 `lint:boundaries`。明确不鼓励 barrel 文件：提供多个小入口，避免通过一个 index 重导出整个子树。保持精简，放一份可复制的目录示例，再用五个短段落说明五条规则。

随后在仓库的 agent 指令文件中添加一个**上下文指针**：优先使用已有 `CLAUDE.md`，其次使用 `AGENTS.md`，两者都没有时创建 `AGENTS.md`。一行即可，例如：`包按深模块组织：新增或导入包之前，先阅读 [src/packages/README.md](./src/packages/README.md)。` 根据实际包路径调整链接，让 agent 在动手前找到边界约定。

**完成标准：** `<packages-root>/README.md` 已记录约定并明确不鼓励 barrel 文件，仓库 `CLAUDE.md` 或 `AGENTS.md` 中有指向它的链接。

## 注意事项

- 配置中的 `$1` 反向引用使用 dependency-cruiser 的捕获组匹配，让包能访问自身实现，同时限制包外调用方。保留这套通用规则，无需展开成逐包配置。
- 公共和私有按**路径深度**区分：包根目录文件是入口，子目录内容是私有。`lib/` 和 `tests/` 是约定目录；边界规则对任意子目录都生效，因此新增内部目录无需改配置。添加入口只需增加一个根目录文件，无需 barrel。
- 包目录保持**扁平**：包只能是包根目录的直接子目录。包内实现可以任意嵌套，但包里不再嵌套其他包。
- 配置使用 `.cjs`，让 `module.exports` 在设置了 `"type": "module"` 的仓库中也能工作。
