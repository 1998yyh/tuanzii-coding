# UI 原型

在同一条路由上生成**数个截然不同的 UI 变体**，通过悬浮底栏切换。用户在浏览器里来回翻看，选中一个（或者从每个里各偷一点），然后把剩下的扔掉。

如果问题关乎逻辑/状态而不是外观——走错分支了。用 [LOGIC.md](LOGIC.md)。

## 什么时候用这个形态

- “这个页面应该长什么样？”
- “定下来之前，我想看这个 dashboard 的几个方案。”
- “给设置页换个布局试试。”
- 任何用户本来要在脑子里对着三个模糊 mockup 纠结一整天的场合。

## 两种子形态——强烈优先子形态 A

UI 原型在**与应用其余部分紧挨着**时更容易评判——真实的 header、真实的侧栏、真实的数据、真实的密度。孤立的用完即弃路由是真空环境：每个变体单独看都挺好。只要有一个合理的现有页面能承载变体，就默认用子形态 A。只有当原型确实没有邻近的栖身之处时才用子形态 B。

### 子形态 A——对现有页面的调整（首选）

路由已经存在。变体渲染在**同一条路由**上，用 `?variant=` URL search param 门控。现有的数据获取、params、auth 全部保留——只换渲染部分。这是默认选择；除非有具体理由，否则选它。

如果原型针对的东西还没有页面、但*自然会住在某个页面里*（dashboard 的新版块、设置页的新卡片、现有流程的新步骤）——那仍然是子形态 A。把变体挂载进宿主页面。

### 子形态 B——新页面（最后手段）

只有当被原型化的东西确实没有现有页面可住时才用——比如一个全新的顶层界面，或者一个没法合理嵌入任何地方的流程。

按照项目已有的路由约定创建一条**用完即弃路由**——不要发明新的顶层结构。命名上要让人一眼看出是原型（例如在路径或文件名里带上 `prototype`）。同样用 `?variant=` 模式。

在确定用子形态 B 之前，先自查：真的没有任何现有页面可以嵌入它吗？空路由会掩盖 populated 页面才会暴露的设计问题。

两种子形态里，悬浮底栏完全一样。

## 流程

### 1. 写下问题，定下数量 N

默认 **3 个变体**。超过 5 个就不再是截然不同，而开始变成噪音——以此为上限。

用一行字写下计划，放在原型所在位置或文件顶部注释里：

> “设置页的三个变体，在现有 `/settings` 路由上通过 `?variant=` 切换。”

无论用户在场与否、能否反驳，这句话都管用。

### 2. 生成截然不同的变体

起草每个变体。每个都要满足：

- 页面的用途和它所能访问的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，不论是什么）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体之间必须**结构性不同**——布局不同、信息层级不同、主要 affordance 不同，而不只是配色不同。三个微调过的卡片网格不是 UI 原型，是墙纸。如果两个草稿出来太像，就带着明确的“不许用卡片网格”约束重做一个。

### 3. 把它们接线起来

在路由上创建一个切换组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：切换器之上的所有现有数据获取保持不动；只有渲染的子树随变体变化。

子形态 B（新页面）：`/prototype/<name>` 下的用完即弃路由挂载同一个切换器。

### 4. 构建悬浮切换器

一个固定在屏幕底部中央的小条，由三部分组成：

- **左箭头**——切到上一个变体（循环回绕）。
- **变体标签**——显示当前变体 key，如果变体导出了名字，也一并显示。例如 `B — 侧栏布局`。
- **右箭头**——切到下一个（循环回绕）。

行为要求：

- 点击箭头更新 URL search param（用框架的 router——Next 上是 `router.replace`，React Router 上是 `navigate`，等等），让变体可分享、刷新后保持稳定。
- 键盘：`←` 和 `→` 方向键同样切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 处于焦点时不要拦截方向键。
- 视觉上与页面区分开（例如高对比度的胶囊形、轻微的阴影），让人一眼看出它不属于被评估的设计。
- 在生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价检查门控，这样误合并的原型也不会把底栏发给用户。

把切换器做成单个共享组件，让两种子形态复用。放在项目里共享 UI 所在的位置。

### 5. 交出去

把 URL（和 `?variant=` 的 key）亮出来。用户有空时会自己翻看。最有意思的反馈通常是**“我想要 B 的 header 配 C 的侧栏”**——那才是他们真正想要的设计。

### 6. 沉淀答案并清理

某个变体胜出后，沉淀答案——哪个变体、为什么——然后按 [SKILL](SKILL.md) 描述的方式沉淀原型。把胜者折入真实代码，把其余移到用完即弃分支，不进 main：

- **子形态 A**——把胜者折入现有页面；从 main 里删掉落选变体和切换器。
- **子形态 B**——把胜出变体提升为正式路由；从 main 里删掉用完即弃路由和切换器。

完整的变体集合是一手资料，所以它去用完即弃分支，而不是进垃圾桶——留在 main 分支里的变体组件和切换器会迅速腐烂，还会误导后来的读者。

## 反模式

- **变体只在配色或文案上有差异。** 那是微调，不是原型。真正的变体在结构上就有分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就背离了初衷。每个变体都应该有推翻整个布局的自由。
- **把变体接到真实的 mutation 上。** 只读原型就够了。如果某个变体需要写操作，指向一个 stub——问题是“这应该长什么样”，不是“后端能不能用”。
- **把原型直接提升进生产。** 变体代码是在原型约束下写的（没有测试、错误处理最小化）。折入时正经重写一遍。
