# Prototype

原型是**用来回答一个问题的用完即弃代码**。问题决定形态。

## 选择分支

识别要回答的是哪个问题——从用户的 prompt、周边代码判断，或者用户在场就直接问：

- **“这个逻辑 / 状态模型感觉对吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单 HTML 文件——自由按钮加分页的引导式走查——把状态机推过那些在纸面上难以推理的 case，非开发者也能上手操作。
- **“这东西应该长什么样？”** → [UI.md](UI.md)。在同一条路由上生成数个截然不同的 UI 变体，通过 URL search param 和悬浮底栏切换。

两个分支产出的东西差别很大——选错了整个原型就白做了。如果问题确实含糊且联系不上用户，默认选更贴合周边代码的分支（后端模块 → logic；页面或组件 → UI），并在原型顶部声明这个假设。

## 两个分支都适用的规则

1. **从第一天起就是用完即弃，并且明确标记为此。** 把原型代码放在它真正会被使用的位置附近（紧挨它所服务的模块或页面），让上下文显而易见——但命名上要让随便一个读者都看得出这是原型，不是生产代码。用完即弃的 UI 路由要遵守项目已有的路由约定，不要发明新的顶层结构。
2. **启动成本为零。** UI 原型从项目任务运行器的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是一个用户双击即开的 HTML 文件。无论哪种，启动都不需要动脑子。
3. **默认不做持久化。** 状态活在内存里。持久化是原型要_验证_的东西，不是原型应该依赖的东西。如果问题明确涉及数据库，就指向一个scratch 数据库或本地文件，名字要明确标注“PROTOTYPE — 随时可删”。
4. **跳过打磨。** 没有测试，除了让原型_跑得起来_所必需的之外没有错误处理，没有抽象。重点是快速学到东西。
5. **把状态暴露出来。** 每次操作后（logic）或每次切换变体后（UI），打印或渲染出完整的相关状态，让用户看到发生了什么变化。
6. **完成后沉淀。** 把验证过的决策折入真实代码，然后把原型本身作为**一手资料**留存：提交到一个用完即弃分支，不进 main，并在实现 issue 上留下指向该分支的上下文指针。把答案也沉淀下来——结论和它回答的问题——记在 issue 或 commit 里。main 分支只保留验证过的决策。
