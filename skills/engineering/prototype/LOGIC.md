# 逻辑原型

一个自包含的单 HTML 文件——一个**可分享的演示**——让任何人都能通过点按钮来驱动一个状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用——就是那种在纸面上看着合理、但只有推过真实 case 才会感到不对劲的东西。

因为它只有一个文件、无需安装任何东西，你可以把它交给非开发者——设计师、PM、领域专家——让他们亲手感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 什么时候用这个形态

- “我不确定这个状态机能不能处理先 X 再 Y 的边界情况。”
- “这个数据模型真的能表达……这种情况吗？”
- “我想在动手写之前先摸清这个 API 应该长什么样。”
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是“这东西应该长什么样”——走错分支了。用 [UI.md](UI.md)。

## 流程

### 1. 写下问题

写代码之前，先写下你要原型化的状态模型和要回答的问题。一段话，放在演示顶部（做成可见的介绍区，不只是注释）。答错问题的逻辑原型是纯浪费——把问题写明白，之后才能核对，无论用户是现在就在看还是 AFK 之后再回来。

### 2. 把逻辑隔离进一个可移植模块

把真正的逻辑——回答问题的那部分——放进一个单独的 `<script>` 块，写成一个小而纯的模块，之后可以原样提出来放进真实代码库。页面是用完即弃的；这个模块不是。

正确的形状取决于问题：

- **纯 reducer**——`(state, action) => state`。适合 action 是离散事件、state 是单一值的情况。
- **状态机**——显式的状态与转换。适合“当前哪些操作是合法的”本身也是问题一部分的情况。
- **一组操作普通数据类型的纯函数**。适合没有隐式当前状态、只有转换的情况。
- **方法面清晰的类或模块**——当逻辑确实要持有持续的内部状态时。

选最贴合所问问题的形状，*而不是*最容易接到页面上的形状。保持纯粹：不碰 DOM、不碰 `document`、按钮处理器不许伸进它内部。页面调用它；反方向没有任何流动。这正是原型能超越自身生命周期的价值所在：问题一回答完，验证过的 reducer / 状态机 / 函数集可以自己提进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS——没有框架、没有打包器、没有服务器，全部内联，双击即开，邮件转来转去也不会坏。任何人打开就能跑。

为非开发者而写。每个标签都用**领域语言**，不是代码——按钮和状态读起来要像业务，而不是 reducer。用大白话解释正在发生什么。

自上而下按清晰层次布局：

1. **标题和一句话说明**这个演示能让你探索什么（第 1 步写下的问题）。
2. **当前状态**——完整的相关状态，渲染成可读的面板（带标签的字段，不是一坨原始 JSON），每次点击后重新渲染，让变化可见。在有助于非开发者理解的地方，标出刚刚变了什么。
3. **自由按钮**——每个操作一个按钮，始终可用，让任何人可以按任意顺序戳这个模型。每次点击 dispatch 对应操作并重新渲染状态。
4. **引导式走查**——一组**场景**，一个 tab 一个。每个 tab 里放一段场景的大白话描述——它设定的情境和该留意什么——下面按顺序排好这个场景**要按的按钮**。每一步都是真按钮：点击就执行该操作并进入下一步。开始一次走查会重置到已知的初始状态，保证场景每次都以同样方式运行。

挑选能展示别扭 case 的场景——happy path、棘手的边界情况、一次本该非法的尝试——那些在纸面上难以推理的。

保持好看但克制：干净的排版、慷慨的间距、一个强调色。不要动画，不要花哨——任何东西都不能跟状态和按钮抢戏。

### 4. 交出去

把文件发给他们，或者替他们打开。他们有空时会自己点走查和自由探索；有意思的时刻是他们说“等等，这不应该是允许的”或者“咦，我以为 X 会不一样”——这些是_想法_里的 bug，而这正是全部意义所在。他们想要新操作或新场景，就加上。原型是会演化的。

### 5. 沉淀答案和原型

原型回答了它的问题之后，先沉淀答案，再按 [SKILL](SKILL.md) 描述的方式沉淀原型。逻辑原型的对应关系：验证过的 reducer / 状态机 / 函数集提进真实模块（决策被吸收）；HTML 外壳跟着去用完即弃分支，作为一手资料保存原型——作为单个自包含文件，它在那里也随时可以重新跑起来。

## 反模式

- **不要加测试。** 需要测试的原型已经不再是原型。
- **不要接真实数据库。** 除非问题 specifically 关于持久化，否则用内存状态。
- **不要泛化。** 没有“万一以后想支持 X”。原型只回答一个问题。
- **不要把逻辑和页面糊在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就提不出去了。让页面保持为纯模块之上的薄壳。
- **不要动用框架、打包器或服务器。** 接收者双击打开的一个文件；React 应用或 dev server 会毁掉“可分享”。
- **不要把 HTML 外壳带进生产。** 页面是为手工点按优化的。它背后的逻辑模块才是值得保留的部分。
